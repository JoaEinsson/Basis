# Basis interface and interaction contract

Status: **accepted product direction on August 30, 2026**.

This document is the normative source for the Basis application shell,
navigation, library presentation, search presentation, Now Playing layout, and
related interaction behavior. It is a layout and interaction contract, not a
new theme. It supersedes conflicting UI composition examples elsewhere in the
specification, especially the former permanent-sidebar shell. The data model,
portable-state rules, Query/View Engine, Theme Engine, playback rules, and
security boundaries remain unchanged.

When another document conflicts with this one on interface composition or
navigation behavior, follow this document and the numbered decisions in
`DECISIONS.md`.

## Product test

Basis must read immediately as a desktop music player whose main content is the
user's music. If all application chrome were neutral gray, the screen should
still obviously be a music application because artwork, albums, artists,
tracks, lyrics, and playback state dominate the composition.

Application chrome exists only to navigate or manipulate those objects. The
shell must recede behind the music.

## Non-goals for this redesign

This contract does not:

- redesign theme colors or replace the token architecture;
- add multiple simultaneously merged library roots;
- turn folders into the semantic center of the library;
- replace the Query/View Engine with screen-specific query systems;
- make the queue a playlist;
- add a mobile navigation model;
- add structural scripting to themes;
- change any portable, offline, release, or security rule.

The accepted post-MVP extension is `UI_UX_POLISH_PLAN.md`. It specifies a
unified custom Windows/Linux window/application toolbar, Signal Cyan Nocturne
identity, shared interaction primitives, and an expressive but controlled
system-wide motion language without retroactively opening the M0-M8 gate or
changing the ownership boundary below.

## Layout versus Theme Engine boundary

This contract defines application structure, navigation, information hierarchy,
and content composition. It must not override or narrow the existing data-driven
Theme Engine. Layout implementation contains no built-in-theme styling and no
literal visual values that belong to a theme.

The layout/navigation system owns:

- application regions and their structural relationships;
- navigation placement;
- content order and information hierarchy;
- whether a structurally meaningful pane or container exists;
- pane open/close/overlay behavior;
- responsive recomposition;
- entity presentation structure;
- navigation, search, detail, and Now Playing state transitions.

The Theme Engine owns:

- colors;
- typography;
- border radii;
- border appearance;
- shadows and elevation appearance;
- blur and glow;
- spacing density within validated layout bounds;
- artwork treatment;
- focus, selection, hover, and playback-state styling;
- lyric emphasis styling;
- progress styling;
- motion timing and easing;
- every other registered visual token.

All layout components consume semantic or allowlisted component theme tokens.
They never encode Paper-, Nocturne-, or Chromatic-specific values. For example,
a layout component must not contain:

```css
border-radius: 10px;
background: #13151a;
box-shadow: none;
```

It consumes the semantic properties generated by the Theme Engine instead:

```css
border-radius: var(--mv-shape-radius-surface);
background: var(--mv-color-bg-surface);
box-shadow: var(--mv-elevation-surface);
```

The canonical token registry and its one CSS-variable conversion boundary own
the exact property names and fallback values. A feature/layout component may
select the correct semantic role, but it may not define the role's visual value
or parse theme JSON.

A user theme is explicitly allowed to make Basis look substantially different
while preserving the same navigation, information architecture, content order,
and safety/accessibility guarantees. Paper, Nocturne, and Chromatic are theme
definitions, never conditionals inside layout components.

The following wording is normative when reviewing layout:

- Do not introduce containers solely to showcase border radius. Radius itself
  is theme-controlled.
- Do not introduce elevation solely to manufacture hierarchy. Elevation styling
  is theme-controlled.
- Prefer semantic hierarchy and layout over unnecessary containers. Surface
  appearance is theme-controlled.

These rules replace any earlier instruction to prefer a particular radius size,
flatness, shadow amount, glow amount, or surface aesthetic.

## Shell anatomy

The desktop shell has four possible regions:

```text
+---------------------------------------------------------------------+
| APP TOOLBAR                                                         |
| Basis  Back Forward  [pinned Views...]                  Search More |
+---------------------------------------------------------------------+
| OPTIONAL VIEW TOOLBAR                                               |
| result count / filters / grouping / sorting / representation        |
+------------------------------------------------------+--------------+
|                                                      | OPTIONAL     |
|                     MAIN CANVAS                      | CONTEXT PANE |
|                                                      |              |
+------------------------------------------------------+--------------+
| PERSISTENT NOW PLAYING / TRANSPORT                                  |
+---------------------------------------------------------------------+
```

The invariants are:

1. There is no permanent left navigation sidebar.
2. The app toolbar is compact desktop chrome, not a website navbar.
3. The main canvas owns the current library, detail, search, settings, or Now
   Playing state.
4. The secondary View toolbar exists only when the current representation has
   useful view controls.
5. The bottom transport is outside the navigation stack and remains visible
   while music is loaded, including during browsing, search, details, settings,
   and Now Playing.
6. Queue, track information, and similar tools may use a temporary, closable
   context pane. They are never permanent navigation.

### App toolbar

From left to right, the toolbar contains:

- a compact Basis mark/name;
- Back and Forward controls;
- ordered user-pinned Views in the available center space;
- a compact overflow for pinned Views that do not fit;
- Search;
- optional context controls when relevant;
- the application overflow menu.

Settings is available from the application overflow menu and an appropriate
desktop shortcut. It does not occupy permanent primary-navigation space.

The toolbar must not contain a permanent dashboard-style search rectangle.
Inactive search is an icon/button. Activating it expands the toolbar control
and replaces the main canvas with `SearchView`.

### View toolbar

The optional secondary toolbar may contain:

- result count;
- active removable filter chips;
- Add filter;
- grouping;
- sorting;
- Grid/List/Table/Columns representation when supported.

Controls should use a clear icon plus tooltip where the meaning is unambiguous.
This bar must not become a dashboard filter form. Omit it when it has no useful
controls.

### Context pane

Queue, Info, and similar supporting content may open in a right-side pane:

- target width at wide desktop sizes: 320–420 px;
- closable without changing the active main-canvas state;
- overlays or compresses intelligently at medium widths;
- becomes an overlay or dedicated state when the window is narrow;
- must not clear search, View state, scroll position, or selection when closed.

## Data-driven primary navigation

Primary navigation is a presentation of the existing View system. Albums,
Artists, Tracks, Folders, Genres, Favorites, Recently Added, custom filters,
and similar entries are pinned `ViewDefinition` values rather than fixed
application roots implemented by unrelated subsystems.

Users can:

- pin and unpin Views;
- reorder pinned Views;
- hide built-in Views they do not use;
- restore hidden Views;
- create and pin custom Views;
- reach overflowed pinned Views from a compact menu.

Built-ins stay immutable. Editing a built-in duplicates it into a portable
custom View, as specified by the Query/View Engine.

`builtin:home` may appear as a pinned composition destination, but it has no
reserved toolbar slot and can be hidden or unpinned. Its sections remain
reusable View projections under the Home contract; it does not become a
dashboard or welcome page.

`workspace.json` schema v1 retains the serialized field name `sidebar` for
backward compatibility. In Basis 0.1.x its semantic meaning is **the ordered
list of pinned primary-navigation Views**. It must not cause a permanent
sidebar to be rendered. Unknown references remain preserved according to D31.
A future schema migration may rename the field, but this redesign alone does
not justify rewriting existing portable files.

`pinToSidebar` in an existing schema or generated DTO likewise means “pinned to
primary navigation” until a versioned migration replaces the legacy name.

## Explicit navigation model

The main canvas is driven by an explicit, discriminated navigation state. Do
not compose page identity from unrelated booleans such as `showSearch`,
`showAlbum`, or `showPlayerFullscreen`.

The minimum conceptual states are:

```text
LibraryEmptyView
LibraryView(view_id)
SearchView(query)
AlbumView(album_key)
ArtistView(artist_key)
PlaylistView(playlist_id)
NowPlayingView(track_id)
SettingsView(section)
CustomView(view_id)
```

`LibraryView` and `CustomView` use the same Generic View renderer. The distinct
names above describe navigation intent, not separate query subsystems.

Each history entry owns enough serializable or locally restorable UI state to
reconstruct the page:

- route/entity identity;
- search query;
- active filters;
- sorting;
- grouping;
- representation mode;
- pagination/window position;
- scroll position;
- focused or selected entity where practical;
- open context pane when restoring it is not disruptive.

Back and Forward restore the existing state rather than recreating a default
version of the page. Scroll restoration occurs after the relevant virtualized
content is available. Playback state and the persistent transport are not
stored inside a history entry.

Required example:

```text
Albums
  -> Search "Sleep Token"
  -> Album "Even in Arcadia"
  -> Now Playing "Emergence"
  -> Back: exact album state
  -> Back: exact search results and scroll position
  -> Back: exact Albums state
```

Clearing or exiting Search returns to the preceding View. Opening a suggestion
or result pushes a normal navigation entry.

## Library acquisition and empty state

Basis supports one active library root at a time under D04. Copy referring to
“folders” must not be interpreted as authorization to merge multiple roots.

Before a root is selected, the main canvas contains only:

```text
Library

No music folder added.

[ Add folder ]

Add a folder to index your music library.
Basis does not move or reorganize audio files.
```

The secondary text is optional and quiet. “Add folder” opens the native folder
picker for the single active root. It may also replace the active root after an
explicit user action elsewhere in the app.

Do not show a hero, marketing slogan, feature cards, portable-architecture
explanations, `.musiclib` explanations, or a success banner in this flow.

After selection, content should replace the empty state progressively. A small
inline status is sufficient:

```text
Indexing 842 of 1,294 tracks...
```

Individual scan errors remain inspectable without turning the canvas into a
status dashboard. Completion does not produce a celebratory banner.

## Normal library representations

Artwork, typography, alignment, and whitespace provide the primary hierarchy.
Sections are not wrapped in cards merely to create a surface.

### Albums View

Albums defaults to a responsive artwork grid. A grouped example is:

```text
Albums                                      Artist ascending  Grid

A

[cover]       [cover]       [cover]       [cover]
Album         Album         Album         Album
Artist        Artist        Artist        Artist

B

[cover]       [cover]       [cover]
```

The artwork tile is naturally card-like; the surrounding group and page are
not. Pagination/windowing is required for large collections.

### Track View

Tracks uses a virtualized list or table. Selection, keyboard focus, playing,
paused, and unavailable states must be visually distinct without painting the
entire interface with accent color. Columns come from the View definition.

### Album detail

Clicking an album opens a dedicated `AlbumView`. It never scrolls a global list
to simulate album navigation.

The page contains:

- Back context;
- prominent artwork;
- album title, album artist, year, track count, and duration when known;
- Play, Shuffle, and overflow actions;
- only that album's tracks, ordered by disc then track number.

The page itself is the surface. Do not wrap the entire detail in a large rounded
container.

### Artist detail

`ArtistView` contains:

- artist name and concise aggregate metadata;
- the artist's album grid;
- a track section;
- Play and Shuffle actions when meaningful.

Album and track sections are ordinary page sections, not dashboard cards.

### Missing artwork

Use the deterministic album-key fallback required by D54. Missing art should
preserve grid rhythm and entity identity without becoming a decorative feature
card.

## Global search

Search is a first-class main-canvas representation of the indexed library. It
is not merely the command palette and not merely a dropdown.

### Entry and keyboard behavior

- Toolbar Search opens `SearchView` and expands the toolbar search control.
- `Ctrl/Cmd+F` focuses/opens library search.
- `/` opens library search when focus is not inside editable content.
- `Ctrl/Cmd+K` remains the command palette shortcut required by the original
  specification. The palette can navigate to entities or actions, but it does
  not replace `SearchView`.
- `Escape` first closes suggestions; a subsequent Escape with no suggestions
  exits Search and restores the previous View. If product behavior can clear a
  non-empty query without ambiguity, the first page-level Escape may clear it
  and the next exits.
- Arrow keys move through suggestions/results where applicable.
- Enter opens the explicitly highlighted suggestion/result. Without a
  highlighted item, Enter leaves the result canvas visible.

Autocomplete may appear as a small typing aid. It must never be the only result
surface.

### Search coverage

Search covers all indexed or portable user/library metadata useful to
discovery, including at minimum:

- track title;
- artist and album artist;
- album;
- year/date;
- genre;
- composer when available;
- custom tags and overrides when implemented;
- folder/path metadata;
- relevant technical metadata such as codec;
- playlists;
- saved Views;
- other indexed facets that are part of the current MVP schema.

Unavailable future fields do not justify a mock result. They become searchable
when their owning milestone creates the real data source.

### Entity and relationship awareness

Search must return direct entity matches and related entities. It cannot be a
single FTS track list.

For query `Sleep Token`, the result canvas should contain:

- the direct Artist entity;
- albums whose artist or album artist relationship points to Sleep Token, even
  when their titles do not contain “Sleep Token”;
- tracks related to Sleep Token;
- relevant playlists or saved Views when their real indexed definitions match.

For `2025`, results may include the matching year facet plus albums and tracks
released in 2025. For `country`, results may include Genre: Country and related
artists, albums, and tracks. For `FLAC`, results may include matching technical
metadata.

Ranking uses deterministic tiers in this order:

1. exact entity-name match;
2. exact metadata-value/facet match;
3. prefix match;
4. direct fuzzy or textual match;
5. relationally expanded result.

Within a tier, the Query Service uses the locked FTS/BM25 behavior and stable
entity-specific tie-breakers. The frontend must not rerank the entire library.

### Search presentation

Results are grouped by entity kind and rendered in their natural form:

- Artists: compact artist entities;
- Albums: artwork grid;
- Tracks: track list/table;
- Playlists: playlist entities;
- Views: View entries;
- Folders: folder entries;
- Tags/facets: compact facet entries.

Omit empty sections. Do not flatten all results into one track list. Loading,
no-results, parse-error, and backend-error states occupy the main canvas and
preserve the query. A structured-query parse error is visible and never falls
back silently to different semantics.

## Playback navigation and Now Playing

The persistent transport is always outside the main-canvas navigation stack.
It updates playback state in place while the user browses.

### When Now Playing opens

A deliberate primary play action that starts a track or collection opens
`NowPlayingView` by default. Examples include Play on an album and activating a
track with the primary play gesture. `Play next` and `Add to queue` do not
navigate.

Automatic track advance, queue changes, metadata refresh, or lyric refresh
never steals focus. Once the user leaves Now Playing, Basis remains on the page
the user chose while the transport continues updating. Clicking the current
track title or artwork in the bottom transport opens Now Playing explicitly.

### Wide layout

Now Playing replaces the main canvas; it is not a modal. At wide desktop sizes:

- the left region occupies roughly 38–46% of usable width;
- large square artwork is vertically centered and visually dominant;
- restrained track/album information may sit near the artwork;
- the right region provides a comfortable, vertically scrollable lyric column;
- artwork and lyrics sit directly on the page background, not in dashboard
  cards;
- a Show/Hide Lyrics action recomposes the page; it does not merely make the
  lyric column invisible;
- when lyrics are hidden or the resolved document is explicitly instrumental,
  artwork and track metadata are centered in the available main canvas with no
  empty lyric column;
- a clear Back action restores the source page exactly;
- the bottom transport remains visible.

### Lyrics states

Synchronized lyrics:

- keep the active line near the visual focus with smooth scrolling;
- emphasize the active line using theme tokens;
- keep past/future lines readable but quieter, including after the configured
  inactive opacity is composited on Paper or another light theme;
- wrap each line inside the available column and never introduce a horizontal
  lyric scrollbar; unusually long words use safe overflow wrapping;
- allow a timestamped line to seek when supported;
- suspend follow mode during manual scrolling;
- resume follow mode after a documented interaction timeout or explicit
  follow control, without snapping violently.

Plain lyrics and candidate copy follow the same wrapping and contrast rules.
Loading and missing states are quiet:

```text
Fetching lyrics...
```

```text
Lyrics unavailable
[ Retry ]
```

Lyrics are content, not a widget. They remain bounded and rendered as untrusted
text under the security contract. `color.lyrics.active`,
`color.lyrics.past`, `color.lyrics.upcoming`,
`color.lyrics.translation`, `component.lyrics.activeScale`, and
`component.lyrics.inactiveOpacity` remain editable Theme Engine values. The
editor previews their effective appearance and warns when resolved contrast is
insufficient.

The Show/Hide Lyrics preference is device-local and persists across track
changes. An explicitly instrumental document temporarily forces the same
artwork-only composition without changing that preference. The next
non-instrumental track restores the user's prior mode. A missing lyric or
provider error does not imply instrumental: Basis retains the unavailable/error
state and its retry action.

## Responsive recomposition

Basis is desktop-first and supports resizable windows. Breakpoints are layout
guidance; components must also react to actual available space.

### At least 1200 px

- show the full primary toolbar when space permits;
- use wide album grids;
- show artwork and lyrics side by side in Now Playing;
- allow the optional right context pane.

### 800–1199 px

- move lower-priority pinned Views into overflow;
- reduce grid columns and artwork size;
- retain the Now Playing split only while both regions remain usable;
- overlay or intelligently compress the context pane.

### Below 800 px

- use a compact toolbar and overflow pinned Views as necessary;
- stack Now Playing artwork above lyrics;
- move the context pane to an overlay or dedicated state;
- preserve usable control targets instead of shrinking every control;
- recompose toolbars and metadata rather than clipping or horizontal-scrolling
  the whole application shell.

Themes may tune validated dimensions, but may not change these structural
rules.

## Visual composition rules

Prefer semantic hierarchy, content order, artwork proportion, alignment, and
tokenized spacing over unnecessary containers. Cards are appropriate only when
the represented entity is naturally card-like, such as an album, playlist, or
visual collection. The Theme Engine controls what every retained surface or card
looks like.

Do not use:

- a permanent dashboard sidebar;
- hero sections or giant web headings;
- marketing or product-philosophy copy in normal flows;
- eyebrow labels used as decoration;
- feature or explanatory cards;
- generic cards around text and sections;
- readiness/success banners such as “bridge ready”;
- a permanent giant search field;
- containers introduced solely to showcase border radius;
- elevation or surface wrappers introduced solely to manufacture hierarchy;
- hard-coded accent, border, shadow, glow, radius, or surface values in layout
  components;
- a welcome/landing-page composition.

Page titles use the semantic title role appropriate to the desktop information
hierarchy; the Theme Engine controls its exact typography. Empty states remain
quiet. The page background is a valid structural surface. Separators are used
only where they communicate grouping, and their appearance is theme-controlled.
Album artwork is allowed to be large.

Existing Basis semantic theme tokens remain authoritative. Obsolete
sidebar-named tokens may remain in the versioned registry for compatibility,
but they cannot reintroduce a permanent sidebar or alter navigation structure.
Layout components request semantic interaction, focus, selection, and playback
roles; the Theme Engine determines their visual treatment.

## Accessibility and desktop interaction

- Every toolbar action has an accessible name and tooltip when icon-only.
- Back, Forward, Search, overflow, context-pane controls, transport, and View
  controls are keyboard reachable with visible focus.
- Focus order follows the visual order: app toolbar, optional View toolbar,
  main canvas, context pane, transport, while direct shortcuts remain usable.
- Reordering pinned Views has a keyboard-accessible alternative to drag and
  drop.
- Grid/list/table entity activation is available without a pointer.
- Reduced motion affects navigation, artwork accent changes, and lyric
  auto-scroll behavior without removing state clarity.
- Dynamic content updates announce concise state changes where useful; scan and
  playback events must not flood assistive technology.
- Minimum control targets and text contrast follow the Theme Engine safety
  corrections.

## Required states by surface

Every primary surface must define and test applicable states:

| Surface | Required states |
|---|---|
| Library acquisition | no root, choosing, initializing, actionable failure |
| Generic View | loading, progressive results, empty, populated, query error, backend error |
| Search | inactive, typing, loading, grouped results, no results, parse error, backend error |
| Album/Artist detail | loading, populated, missing entity, partial metadata, unavailable artwork |
| Now Playing | no current track, loading track, playing, paused, recoverable playback error |
| Lyrics | loading, synchronized, plain, unavailable, retryable provider error, manual-scroll mode |
| Context pane | closed, open, loading, empty, error |
| Transport | hidden/no session, loading, playing, paused, ended, recoverable error |

Errors should be local to the failed surface. A lyric or artwork failure must
not replace the player; a scan-file failure must not replace the library.

## Milestone ownership

This design is delivered incrementally without temporary competing shells:

- M2 owns headless entity queries, relational search support, Generic View DTOs,
  album detail data, and artist detail data. It creates no provisional shell,
  route presentation, or disposable visual implementation.
- M3a owns the top toolbar, pinned-View navigation, SearchView presentation,
  explicit history/restoration, Generic View renderers, album/artist pages,
  responsive structure, keyboard behavior, semantic token consumption, and
  removal of dashboard composition. It is the first complete interface phase.
- M3b supplies all appearance through semantic tokens; it does not alter shell
  structure.
- M4 owns the persistent transport, deliberate playback navigation, Now Playing
  playback state, and queue context pane.
- M5 adds real playlist/View search results and event-derived Views.
- M6 completes the Now Playing lyric region and its synchronized/plain/error
  states.
- M8 owns responsive verification, accessibility polish, and the final
  anti-drift audit.

Later milestones extend the one shell; they must not introduce placeholder
sidebars, dashboards, hero screens, or separate search systems while waiting for
their backend features.

## Acceptance scenarios

### UX01 — relational artist search

Given the library contains artist Sleep Token and albums `Sundowning`, `This
Place Will Become Your Tomb`, `Take Me Back To Eden`, and `Even in Arcadia`,
searching `Sleep Token` in SearchView shows the Artist result, all four album
covers, and related tracks even though the album titles do not contain the
query.

### UX02 — album to Now Playing and back

From Albums, open `Even in Arcadia`, start `Emergence`, and verify Now Playing
opens with artwork left, synchronized lyrics right when available, and the
persistent transport below. Back restores the exact album page and scroll
position.

### UX03 — search history restoration

Search `Sleep Token`, open `Even in Arcadia`, start a track, then press Back
twice. The first Back restores the album; the second restores the exact prior
search query, grouped results, selection, and scroll position.

### UX04 — playback never steals focus

While a track is playing, leave Now Playing for Albums. When the track ends and
the next queue item starts, Basis stays on Albums and only the transport updates.

### UX05 — explicit transport navigation

Click the current-track artwork or title in the bottom transport. Now Playing
opens as a normal navigation entry; Back restores the previous canvas.

### UX06 — data-driven pinned navigation

Pin, unpin, hide, restore, and reorder built-in and custom Views. Resize until
the toolbar overflows, restart Basis, and verify order/visibility persists and
no permanent left sidebar appears.

### UX07 — responsive recomposition

Exercise widths above 1200 px, between 800 and 1199 px, and below 800 px. Verify
navigation overflow, grid reflow, context-pane behavior, stacked Now Playing,
usable controls, and no app-shell horizontal overflow.

### UX08 — anti-dashboard audit

Inspect every MVP route and search the source for obsolete composition. No
route contains a hero headline, feature explanation cards, success/readiness
banner, permanent giant search field, permanent navigation sidebar, decorative
information cards, or marketing copy.

### UX09 — theme freedom without layout drift

Apply two valid test themes with deliberately different typography, density,
radius, border, elevation, glow, artwork, state, lyric, progress, and motion
treatments. Both must preserve the same toolbar/navigation placement, View and
detail hierarchy, context-pane behavior, Now Playing composition, responsive
recomposition, content order, keyboard order, and safety controls. Source
inspection finds no built-in-theme literal or Paper/Nocturne/Chromatic branch in
shell/layout components.

## Pre-merge anti-drift checklist

Before accepting a shell, navigation, search, detail, player, or lyrics change:

- Is music content visually stronger than application containers?
- Is primary navigation composed from pinned Views?
- Is Search a main-canvas state with entity-grouped results?
- Does Back/Forward restore state instead of reset it?
- Is the bottom transport outside navigation history?
- Can automatic playback advance without changing the current canvas?
- Are album/artist details real pages rather than global-list scroll tricks?
- Are filters/sort/group/layout controls using the same View definition?
- Are cards limited to naturally card-like entities?
- Does the narrow layout recompose rather than merely shrink?
- Are all visual values sourced from semantic theme tokens?
- Could a user theme substantially change radius, elevation, glow, typography,
  density, motion, and surface treatment without changing this layout code?
- Are loading, empty, error, keyboard, focus, and reduced-motion states covered?

Any “no” keeps the relevant milestone gate open.
